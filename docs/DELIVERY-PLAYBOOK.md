# Flight Recorder delivery playbook

The owner requested proportionate delivery checks on 27 October 2026. This playbook governs ordinary product and documentation changes. Existing product invariants, explicit task limits, consequential-action approvals and registered workflow safeguards remain in force.

## One delivery loop

Define one outcome and its acceptance criteria. One builder implements it, runs the checks below, resolves ordinary failures within the approved scope, and records one concise result. Update affected documentation in the same change. Commit coherent work and publish it only under the task's actual authority. Verify the required GitHub checks on the exact candidate before integration.

A failed check normally calls for diagnosis and a bounded correction, not another owner approval. Escalate a change to the product promise, historical semantics, security/data boundary, consequential dependency, spending, live provider authority, destructive action or production deployment. Explicit task prohibitions still control.

## Checks follow the risk

| Change | Local verification | Independent review |
| --- | --- | --- |
| Factual text and links | Check the claims and run applicable documentation checks | Required for material product, security or operating-instruction changes; ordinary wording uses normal review |
| Layout or styles | Check the affected views, visual/keyboard behavior and relevant UI/theme tests; keep shared stylesheet boundary guards | Required when access or data-display semantics change; ordinary cosmetic work uses normal review |
| Domain logic, ingestion, replay or attribution | Relevant invariant/property tests and failure paths, preserving schema/artifact identities | Nonauthor review of the affected semantics |
| Authentication, permissions, secrets, migrations or external writes | Adversarial boundary/failure tests and the scoped sandbox qualification, recovery or disable checks | Nonauthor review before integration/release under the applicable gate |

Normal required GitHub CI still runs in full. Do not reduce assertions, skip failing invariants or substitute local results for remote CI. A platform-specific fix needs evidence on the affected platform.

Use targeted local checks and required remote CI. Do not repeat a full local suite, independent review, browser session or qualification solely because another chat takes over unchanged bytes. Repeat or broaden checks when the changed behavior, a failure or an unresolved risk justifies it. A small style edit does not require workflow installation or runtime requalification. The separately scoped workflow procedures in AGENTS section 12 still govern an actual workflow adoption/dispatch operation.

## One completion record

Record the implemented revision, behavior, tests/run URL and result, important limits, publication/deployment status and next action. Distinguish tests executed from logs inspected. Reference the existing evidence instead of copying it into a chain of sign-off packets. Never invent a fingerprint or overwrite failed evidence to conceal it.

Detailed preservation receipts are appropriate for credential handling, retained-data changes, live authority and contested provenance. They are not a default requirement for every text or style change. Preserve relevant failures and original evidence in the existing private handoff location.

STATE remains the sole live status record, maintained by the coordinator. Keep it concise and current; Git retains history. A dated review packet is evidence, not another tracker. README and setup guides must distinguish public synthetic demonstration, fake-tested behavior, bounded provider proof and production qualification.

## Ownership and continuity

Direct coordination among current Flight Recorder project chats is authorized. The owner is not a message relay. Refresh actual role/session metadata before routing a handoff. At a necessary session transition, save and verify the continuation, preserve running jobs and their handles, and verify pickup. Do not restart finished checks or create a successor merely to demonstrate the process.

This playbook grants no new standing push/merge, deployment, spending, account, credential, customer-data or CRM-write permission. It does not authorize native desktop control or bypass a host approval rejection. Continue ordinary approved work; request only a genuinely unresolved consequential decision.
