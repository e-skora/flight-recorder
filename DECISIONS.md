## Ratified Decisions

### D-001 — Product form: web application with a versioned decision-event ingestion API

- **Decision:** The MVP is a web application plus a small collector API at `POST /api/v1/decision-events`. It is not fundamentally an MCP server; an MCP or agent-query interface is a possible post-MVP extension and is an explicit MVP non-goal.
- **Why:** The proof is that a real workflow could instrument a decision and an operator could inspect and replay it. An MCP surface would add a second interface without strengthening that proof.
- **Provenance:** `02` §2 (Product Form), §5.1, §11. Status: ratified 2026-09-01.

### D-002 — Primary user and organizational ICP

- **Decision:** The primary user is a GTM engineer, technical RevOps operator, or revenue-systems owner responsible for automated account-prioritization logic at a scaling B2B SaaS company. The organizational ICP is the category (lean technical GTM team, thousands of accounts, signal-based automation, fragmented stack, changing logic, evaluable outcomes; ~75–500 employees as design center), not a named company.
- **Why:** A narrow, technical primary user makes the semantics (provenance, versioning, replay) the product rather than dashboard polish, and keeps the ICP from collapsing into one reference company.
- **Provenance:** `02` §2. Status: ratified 2026-09-01.

### D-003 — Exactly one fully replayable decision class: account prioritization

- **Decision:** The MVP fully supports replay for account prioritization (`PRIORITIZE` / `DO_NOT_PRIORITIZE`) only. Discovery, enrichment, persona selection, outbound action, and outcome events are required in the trace but are not independently replayable. Additional replayable classes are post-MVP.
- **Why:** One decision implemented completely demonstrates more engineering and product judgment than several implemented superficially.
- **Provenance:** `02` §4; `04` principle 5. Status: ratified 2026-09-01.

### D-004 — Canonical fixture: RelayBridge evaluates NovaSignal AI; Merge is a public reference archetype only

- **Decision:** The fictional demo operating company is **RelayBridge** (B2B integration and agent-connectivity platform). The canonical fictional prospect is **NovaSignal AI**. **Merge** is cited only as public evidence that the operating archetype exists and MUST NOT appear as a customer, tenant, or ledger account, nor be described as lacking internal observability. The canonical facts (boundary `2026-04-17T10:05:02Z`, employees 184, industry B2B AI Software, US HQ, Series B 18 days prior, 7 open platform-engineering roles, Head of Platform joined 43 days prior, verified integration pressure LOW, workflow `v4.2`; `v3.2` → 86 / `PRIORITIZE`; `v5.1` → 51 / `DO_NOT_PRIORITIZE`; threshold 75; play `#14`, cost `$1.42`, 90-day window, direct attribution, no reply/meeting/opportunity; no confidence emitted) are fixed in `PRODUCT.md` §7 and MUST come from one canonical source in the codebase.
- **Why:** A consistent fictional company avoids overclaiming a customer relationship while keeping the demo grounded in a verified real-world pattern. Fixing the numbers makes AC-01/AC-02 exact and keeps UI, tests, screenshots, and README aligned.
- **Supersedes:** The Acme Robotics / Industrial Automation / VP Sales / 82%-confidence example used in `01-GTM-FLIGHT-RECORDER-SPEC.md`, `03` §4 and §10, `04` principle 9, and `06-PORTFOLIO-OBJECTIVE.md` §5 and §11. Those references are lower-authority illustrations and are superseded wherever they conflict.
- **Provenance:** `02` §2 (roles table), §5.2, §5.7, §8; `05` INV-03 and INV-10. Status: ratified 2026-09-01.

### D-005 — Deterministic core; scoring logic stored as immutable declarative data with hash and evaluator identity

- **Decision:** The replayed decision class uses deterministic logic. Scoring logic is stored as immutable declarative artifacts (factors, weights, missing-value behavior, threshold, output mapping, schema version, activation metadata, canonical content hash, evaluator-code version). Changing any of these yields a new identity. Exact replay verifies hash and evaluator identity first and fails explicitly otherwise. No LLM call is required in the core decision or replay path; any LLM output is labeled explanation, never evidence.
- **Why:** Exact reproduction of a historical decision is the product's central claim; a version label pointing at mutable code cannot support it, and a nondeterministic core cannot be tested against the acceptance criteria.
- **Provenance:** `02` §6.4, §6.5, §6.9, §11, §12; `05` INV-05, INV-07; `04` principle 6. Status: ratified 2026-09-01.

### D-006 — Collector contract: versioned envelope, canonical-JSON idempotency, atomic failure, seed enters through the collector

- **Decision:** One ingestion boundary, `POST /api/v1/decision-events`, with envelope fields `schema_version`, `event_id`, `event_type`, `source`, `account_ref`, `occurred_at`, `recorded_at`, `payload`. Idempotency is defined by equality after schema validation and canonical JSON serialization; conflicting reuse of an `event_id` and invalid envelopes fail visibly without partial writes. The canonical demo seed enters through this boundary (tests may call the underlying service directly). At least one documented example shows a Clay HTTP step, n8n workflow, or equivalent submitting a decision.
- **Why:** Instrumentability is one of the five proof claims; if the demo data bypassed the collector, the boundary would be untested theater.
- **Provenance:** `02` §5.1, AC-15; `05` INV-11. Status: ratified 2026-09-01.

### D-007 — Outcome attribution policy `outcome-attribution-v1`

- **Decision:** Decision-level credit uses a named, versioned policy: (1) valid explicit source-provided action/decision reference; (2) otherwise the most recent eligible outbound action for the same account before the outcome and within 90 days; (3) otherwise unresolved. Eligible actions are actual, recorded, sent/completed outbound actions linked to a prioritization decision for the same account; counterfactual and failed-to-execute actions are ineligible. Results record policy version, method, window, references, time, and status `direct` / `inferred` / `unresolved`. Unresolved outcomes stay visible and out of decision-level metrics; inferred attribution is labeled heuristic.
- **Why:** Silently crediting every account outcome to every preceding decision would make the Insights view dishonest and blur original and counterfactual results.
- **Provenance:** `02` §6.7, §6.8, AC-16; `05` INV-08. Status: ratified 2026-09-01.

### D-008 — Synthetic data only; seeded deterministic dataset with three planted, manifest-declared effects

- **Decision:** All Apollo-, Clay-, CRM-, and outcome-like events are simulated and disclosed as such in product and README. No live third-party API or paid credential is used. The dataset is deterministic and seeded, with at least 200 accounts, and plants exactly three documented effects (neutral `recently_funded`; positive `verified_integration_pressure = HIGH`; `v4.2` workflow underperformance) whose expected values live in a machine-readable manifest separate from the analytics code. Analytics must recover them from ingested events; the UI must not hard-code the conclusions.
- **Why:** Synthetic integrations prove the architecture without spending the MVP on credentials and plumbing, and planted effects make the Insights calculations verifiable rather than decorative — provided they are labeled as demonstration data, not market findings.
- **Provenance:** `02` §5.7, §9, AC-12, AC-13, AC-14; `05` INV-10; `04` principles 7 and 8. Status: ratified 2026-09-01.

### D-010 — Implementation stack, tooling, and repository layout

- **Decision:**
  - **Language:** Python, pinned to 3.13 via `.python-version`.
  - **Web framework:** FastAPI with Pydantic v2 for envelope validation and server-rendered HTML via Jinja2 templates. No JavaScript framework and no bundler; small amounts of vanilla JS or HTMX MAY be added inside a task if a page needs it. FastAPI's generated OpenAPI page serves as the published collector schema.
  - **Database:** SQLite, one file, accessed through SQLAlchemy 2.0. Timestamp convention (binding, because SQLite has no timezone-aware type): every timestamp is validated as timezone-aware at the Pydantic boundary, converted to UTC, and stored as ISO-8601 text with an explicit `Z`; naive datetimes are rejected. Same-instant ordering at a decision boundary uses a recorded sequence number, never display precision. Protected records (decisions, evidence versions, historical context, consumed inputs, original explanations) are append-only in code and additionally guarded by SQLite triggers that raise on UPDATE/DELETE, so a violation fails visibly. Schema is created from SQLAlchemy metadata; a fresh seeded reset is the only "migration" for the MVP. Alembic is added only if a persisted database must survive a schema change.
  - **Tests:** pytest with Hypothesis for property-based and generative cases; FastAPI `TestClient` (httpx) for collector contract tests. Tests are named by contract ID under `tests/invariants/` (INV-01…INV-11) and `tests/acceptance/` (AC-01…AC-18). Hypothesis uses a modest local profile and a larger CI profile.
  - **Lint/format:** ruff only. No type checker for now.
  - **CI:** GitHub Actions on push and pull request: install uv → `uv sync` → `ruff check` → `pytest`, with the invariant suite as a separately named job so its result is visible by name. A README badge references it (Phase 5).
  - **Project tooling:** uv manages the Python version, `pyproject.toml`, and `uv.lock`; documented setup is install uv → `uv sync` → `uv run`.
  - **Layout:** `src/flight_recorder/` with modules mirroring `PRODUCT.md` §6 concepts (`collector/`, `ledger/`, `logic/`, `replay/`, `attribution/`, `analytics/`, `web/`); `fixtures/canonical/` (NovaSignal AI trace as collector envelopes plus logic artifacts `v3.2` and `v5.1`) is the single canonical source for shared demo constants that code and tests load and never re-declare; `fixtures/dataset/` holds the seeded generator config and planted-effects manifest; `fixtures/examples/` holds the Clay / n8n example payload; `scripts/` holds seed (through the collector) and reset; `tests/invariants/`, `tests/acceptance/`, `tests/unit/`; `.github/workflows/ci.yml`. `README.md` arrives in Phase 5.
- **Why:** Python is the working language of GTM engineering and the one the builder can defend; Hypothesis is the strongest property-based testing library available and AC-18 requires generative cases. FastAPI gives schema validation before any write and a documented collector contract for free. SQLite with no server satisfies "run locally from documented steps", "no production credentials", "fresh seeded reset", and "minimize moving parts" directly, and principle 10 forbids infrastructure for hypothetical scale; SQLAlchemy keeps a later PostgreSQL switch a configuration change. GitHub Actions provides the visible CI evidence the portfolio gate requires on the repository that already exists. The `src` layout and ID-named tests make invariant tests easy to locate, as `PRODUCT.md` §11 asks.
- **Tradeoffs accepted:** server-rendered pages are less interactive than a React front end; SQLite carries a weaker production signal than PostgreSQL and requires the explicit timestamp convention above; Hypothesis tests are slower than example tests; uv is one more tool for a reader to recognize.
- **Rejected alternatives:** TypeScript / Next.js / Vitest / fast-check (richer UI, weaker generative testing, build pipeline, less defensible for the builder); Django (unneeded ORM/admin/migration weight); Flask (validation and API docs would be hand-built); PostgreSQL (setup and CI service cost without strengthening the proof).
- **Provenance:** Recommended by the coordinating Claude session and approved by the user on 2026-09-02 as the choice among options `02` §12 leaves open ("any reasonable web stack and relational database"). Status: ratified 2026-09-02.

### D-011 — Phase 3 scope: counterfactual engine first, computed on demand and never persisted; browser replay experience is the next milestone

- **Decision:** Phase 3 is split into 3A and 3B. **3A** builds the counterfactual engine and its proofs only: a `replay` path that re-verifies and reproduces the original decision, reads the same sealed historical context through the same code path, evaluates it under an explicitly selected and verified current artifact, and returns a result typed and labeled as a counterfactual; a structured comparison exposing both logic identities, scores, thresholds, outputs, contribution changes (changed, added, removed, reweighted) with evidence references, and every input current logic expects that the historical context lacks, with `unavailable` and `absent` distinct; and automated tests for AC-02, AC-06, the counterfactual halves of AC-03 and AC-04, AC-07 for the current artifact, and INV-06. Counterfactual results are computed on demand and are **not persisted**: no table, column, event, or cache holds one. 3A's completion is "counterfactual engine complete", not "replay experience complete" or "MVP proven". **3B**, the next milestone and required product work, is the smallest browser experience in which a viewer inspects the original decision and its historical evidence, runs replay, and sees the contribution differences and the counterfactual label: one decision-detail screen with a replay panel (§4.4 and §4.5 together) is acceptable. Missing-input coverage in 3A uses a distinct test-only artifact with its own identity; canonical `v5.1` is unchanged and is not claimed to require `website_intent`.
- **Why:** The 86 → 51 comparison is the central replay moment, and its correctness (no present-day evidence entering, original never blurred with the counterfactual) must be proven at the engine level before a screen displays it; a screen built first would be reviewed for layout while the semantics were still unproven. Persisting counterfactuals is not required by any acceptance criterion, would add a protected table and a persistence story to INV-06 for no proof value, and can be added later by a further decision if a real need appears. Naming 3B now as required work keeps demo readiness on the plan rather than behind unspecified backend work.
- **What stays true:** The complete MVP still requires the collector-backed canonical trace, action, cost and outcome context, explicit attribution, and event-derived aggregate Insights; the build-complete and portfolio-ready gates (including the 30-second understanding and the 60–90 second demo) are unchanged; RelayBridge and NovaSignal AI remain the fictional canonical roles; canonical results (`v3.2` → 86 / `PRIORITIZE`, `v5.1` → 51 / `DO_NOT_PRIORITIZE`, threshold 75) are preserved; no rule editor, no additional replayable decision class, no live vendor integration.
- **Provenance:** `02` §4.5, §5 ("Three things stay distinct", "Replay honesty"), §9 AC-02, AC-03, AC-06, §10 INV-03, INV-06, INV-09, §13 principles 1, 5, 9, 10; user's decision packet 2026-09-08 choosing Option A among the three scoping options put by the coordinating Claude session (A: engine and proofs; B: A plus the comparison page; C: persisted counterfactuals). Status: ratified by user decision 2026-09-08.

### D-012 — Phase 3B presents recorded outcomes without attribution; the complete `outcome-attribution-v1` engine is Phase 4

- **Decision:** Phase 3B stays presentation-only. The decision-detail screen renders recorded outcome observations with their available type, time, and evaluation-window information, and shows `Attribution not yet evaluated` where `PRODUCT.md` §4.4 requires an attribution status. That wording is a presentation state meaning no attribution evaluation exists yet: it is not a fourth `outcome-attribution-v1` result, it is never substituted for `unresolved`, and it is never persisted. Attribution means policy-based linkage under D-007, not proof of causation. Until attribution exists, outcome observations are labeled at their actual scope (recorded account outcomes); account membership alone MUST NOT imply that an outcome belongs to a particular decision, and a source-provided action or decision reference is displayed as a recorded reference without any claim that it has been validated. Missing outcome data, an explicitly recorded open-window state, and recorded negative outcomes stay distinct, and no outcome-evaluation logic is added to manufacture any of those states. Phase 4 implements the complete D-007 policy and replaces the placeholder with policy-backed `direct`, `inferred`, or `unresolved` results carrying policy version, method, window, references, and attribution time, with inferred attribution labeled heuristic. The placeholder does not satisfy §4.4's attribution-status requirement, AC-16, or the attribution and open-window clauses of INV-08; those remain open.
- **Why:** This is a sequencing decision, not a reduction of the MVP requirement. It delivers the inspectable decision and replay screen that D-011 names as required product work while preserving one coherent attribution implementation. Implementing only the direct-reference case now would introduce partial policy semantics into a phase scoped as presentation over proven data, and could label an inferable outcome unresolved.
- **What stays true:** D-007's complete policy, historical-context sealing, immutable logic identity, canonical scoring behavior, and the separation of original and counterfactual results are unchanged. Actual outcomes are never attributed to counterfactual decisions or actions.
- **Provenance:** `02` §4.4, §5 ("Outcomes are later, separate observations", "Outcome attribution policy"), §9 AC-16, §10 INV-08, INV-09, INV-10; D-007, D-011. Status: ratified by user decision packet 2026-09-09.

### D-013 — Phase 4 scope: attribution is a persisted record written through the collector, outcome schema v2 carries source references and window state, delivery splits into 4A and 4B

- **Decision:**
  - **Persistence (Q1).** An attribution result is a durable record, not a view. It enters through the collector as a new event type (`outcome.attributed`) and is written to a new append-only projection. The record carries its own identity, the outcome identity and version it evaluates, the policy version and method, the applied attribution window, the resolved action and decision references when resolved, the attribution time, the status `direct` / `inferred` / `unresolved`, and an inspectable reason for any unresolved or fallback result. The envelope's `account_ref` is the outcome's own account, with an explicit internal attribution source, so an account's attribution appears in that account's trace; `_system` stays a registry sentinel excluded from account surfaces and is never treated as an authentication principal. The collector verifies that a submitted result agrees with the named policy recomputed over a reproducible ledger snapshot; resolving foreign keys alone would let an arbitrary submitted `direct` claim become authoritative, so policy evaluation is shared code between the computation path and the validation path. Each result records a collector-owned ingestion cutoff (or equivalent stable snapshot identity): attribution reads actions recorded by that cutoff, their event times, and the exact outcome version, so a later-arriving action with an earlier occurrence time can never silently change an existing attribution, though it may justify an explicitly appended replacement evaluated against a newer cutoff. Revision uses explicit supersession links; prior rows are retained; cross-outcome links and ambiguous branching are rejected; exactly one effective result is exposed per outcome version and policy. A retry of the same operation reuses its identity and timestamp and has one domain effect, and a new event id must not create a second effective result for the same operation. Results are computed and submitted by a small explicit command or service invocation; browser reads stay read-only; no scheduler, queue, or background platform is introduced.
  - **Outcome schema v2 (Q2).** Schema v1 validation and canonical serialization are unchanged, and version-aware handling is added for the outcome payload. v2 carries an optional source action reference and an optional source decision reference, including neither, and preserves those source values separately from policy-resolved references: a supplied source reference is a claim to evaluate, never proof of credit. Under v2 a well-formed but unusable source reference is retained with a reason and D-007's fallback then applies; unknown, cross-account, ineligible, or mutually inconsistent references never yield direct credit; structurally malformed envelopes are still rejected atomically; v1 keeps its existing stricter reference rejection. Raw source references therefore cannot carry the foreign-key constraints that validated attribution targets carry. The decision-only direct-reference case is supported: a valid original prioritization decision reference resolves directly without inventing an action reference, and when both references are supplied their recorded relationship must agree. An explicit action qualifies only as an eligible actual action under `PRODUCT.md` §5. Eligibility is pinned to normalized instants: strictly before the outcome, no more than 90 days earlier, same account, linked to an original prioritization decision, with sent or completed outbound status; ties on equal action occurrence times break deterministically by collector ingest sequence. The policy's attribution lookback is distinct from the outcome's evaluation period.
  - **Window state (Q3).** v2 records an explicit evaluation state, period bounds, and an observation or as-of time, independent of attribution status: an open observation may still carry direct or heuristic linkage, and a closed observation may be unresolved. A false observation in an open window means no observation recorded as of the stated time, never final failure; supplied unknown values are preserved and no false defaults are manufactured. A negative evaluated outcome stays distinguishable from an open observation and from no outcome data, and advancing the browser's clock never creates an evaluation or turns missing data into a negative result. Closing or correcting an observation appends a new version linked to the version it replaces, the earlier observation and its attribution are retained, and the effective outcome-selection path never counts both. v2 validates period ordering and state/as-of consistency. v1 remains the recorded evaluated representation, including the unchanged canonical outcome.
  - **Delivery (Q4, Q5).** Phase 4 extends the existing decision screen only: the outcome section shows the persisted result's status, policy, method, attribution window, resolved action and decision references where present, attribution time, and an explicit heuristic label on `inferred`, distinguishing source-provided from policy-resolved references and whether the credited decision is the one being viewed. Outcomes stay account-scoped, including unresolved ones. `Attribution not yet evaluated` remains for an outcome with no result, distinct from `unresolved` and from an evaluation failure. Superseded results are inspectable within the existing trace and detail surfaces. No separate attribution dashboard or aggregate screen. The phase splits: **4A** = versioned outcome schema, append and supersession representation, the deterministic policy, persisted collector-backed results, canonical attribution generation, and the automated semantic proofs, completing as "attribution engine and persistence complete"; **4B** = the decision screen's outcome and attribution states with rendered-page and visual checks, completing as "attribution experience complete, subject to explicit acceptance and invariant mapping". 4A must not claim all of AC-16 closed while the decision-metrics integration is unimplemented: 4A proves the effective resolved-outcome selection boundary, and the end-to-end metrics exclusion closes through Insights in Phase 5.
- **Why:** `PRODUCT.md` §6 names Outcome Attribution as a record with a stable identifier and an attribution time, and INV-08 gives it append and supersession semantics, so D-011's ephemeral treatment of counterfactuals does not transfer to it. A versioned outcome payload preserves the identity of every already-accepted event while adding the reference and window states D-007 and INV-08 require. Engine and persistence before presentation keeps each review tractable, as it did in Phase 3.
- **Corrected premises (recorded so they are not relitigated):** the coordinating session's Phase 4 packet claimed that every outcome schema v1 accepts must attribute `direct`. That is wrong. `ActionRecordedPayload.status` admits `failed`, and the outcome's reference validator checks only that the action exists, belongs to the same account, and occurred strictly before the outcome; it checks neither execution status nor the 90-day bound. Outcomes referencing a failed or long-past action are accepted today, so `inferred` and `unresolved` are not categorically impossible under v1. The real v1 gap is that an ordinary reference-free observation and an explicit decision-only reference cannot be expressed. The packet also understated the identity risk: the collector hashes the validated model's JSON dump (`envelope.model_dump(mode="json")`), not the submitted bytes, so adding new defaulted fields to the outcome model can change the canonical hash of payloads whose submitted bytes are identical. That is why Q2 is a new schema version rather than an optional field added to v1, and why Q2 and Q3 are decided together.
- **What stays true:** canonical scores 86 and 51, threshold 75, outputs, rules and evaluator identity; sealed historical context; original and counterfactual separation and the rule that no counterfactual is persisted (D-011); synthetic labeling; the single collector boundary; the build-complete and portfolio-ready gates. Existing canonical envelopes stay byte-for-byte unchanged and attribution is added through the collector. No new consequential dependency.
- **Relationship to D-012:** D-012 deferred policy-backed attribution and open-window presentation to Phase 4 and is superseded only in that sequencing respect. Its presentation state survives: an outcome with no attribution result still reads `Attribution not yet evaluated`, which is not a policy result.
- **Provenance:** `02` §4.4, §5 ("Outcomes are later, separate observations", "Outcome attribution policy"), §6 (Outcome Attribution), §9 AC-10, AC-15, AC-16, §10 INV-01, INV-02, INV-06, INV-08, INV-09, INV-10, INV-11; D-007, D-009, D-010, D-011, D-012. ## Open (Intentionally Unresolved)

These are not decisions. The ratified sources leave them open; nothing here may be assumed by an implementer without a recorded decision. Per the responsibility boundaries, a high-lock-in choice is proposed with tradeoffs and ratified by the user; ordinary reversible choices inside an approved task do not need an entry.
